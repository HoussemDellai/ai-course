# Foundry local authentication maintenance

The PowerShell `EnableLocalAuth` function checks the Foundry account every five
minutes (`0 */5 * * * *`, UTC) and uses
`Set-AzCognitiveServicesAccount -DisableLocalAuth $false` only when local
authentication is disabled. It verifies the result and fails visibly if an update
is denied or ineffective. Invocation results are recorded in Application Insights.

Use only with authorization from the policy owner. This is not an Azure Policy
exemption: a deny policy still blocks the update, and remediation can disable
authentication again between invocations. Cold starts, service outages, or failed
runs can extend the interval. Prefer an approved exemption or Microsoft Entra
authentication when possible.

## Infrastructure

[function_governance.tf](function_governance.tf) adds a PowerShell 7.4 Flex
Consumption Function App, storage, monitoring, and a user-assigned managed identity.
The function uses identity authentication for storage. At the owner's request,
storage shared-key authentication and public network access are enabled, with
`SecurityControl = Ignore` and `CostControl = Ignore` tags. These tags are only
effective if the organization's policies explicitly recognize them; they are not
Azure Policy exemptions. Anonymous blob access remains disabled. The identity has
Storage Blob Data Owner on its dedicated storage account and a custom account
read/write role assigned only to the target Foundry account. Azure does not expose
a permission limited to just the `disableLocalAuth` property; account write also
permits changes to other account settings. It does not grant key listing or RBAC
administration.

## Validate and deploy

Run from this directory with PowerShell, Azure CLI, and Terraform installed.
Confirm the intended Azure subscription before applying infrastructure.

```powershell
az login
$env:ARM_SUBSCRIPTION_ID = az account show --query id --output tsv
terraform init
terraform fmt -check function_governance.tf
terraform validate
pwsh -File .\tests\Test-EnableLocalAuth.ps1
pwsh -File .\tests\Test-EnsureRdpAccess.ps1
terraform plan -out=.terraform\governance.tfplan
# Inspect the plan, including any existing Foundry/model changes, before applying.
terraform apply .terraform\governance.tfplan
pwsh -File .\Build-FunctionPackage.ps1
$app = terraform output -raw governance_function_app_name
az functionapp deployment source config-zip --resource-group rg-foundry-701 --name $app --src .terraform\foundry-local-auth.zip
az functionapp function list --resource-group rg-foundry-701 --name $app --output table
```

Substitute the resource group if you change the Terraform prefix. The package
builder requires the versions in
[requirements.psd1](functions/foundry-local-auth/requirements.psd1) to be installed
locally and reports the exact installation command for a missing module. It bundles
them because Flex Consumption does not support managed dependency installation.
The generated package is kept under the ignored Terraform working directory;
rebuild and redeploy it after changing code or module versions. Protect Terraform
state and plan files: the existing Foundry configuration includes sensitive keys.

The app settings identify the subscription, resource group, account, identity, and
timer schedule. The function uses only managed identity, not a developer login.
New role assignments can take several minutes to propagate. Check Application
Insights failures and the Azure activity log for authorization or policy denials.
No HTTP-triggered application endpoint is created.

The explicit empty `AzureWebJobsStorage` setting overrides an invalid empty-key
connection string generated by AzureRM for identity-based Flex deployments.
Keep the `AzureWebJobsStorage__*` identity settings. AzureRM can omit the empty
setting during refresh and therefore show an app-setting-only update on later
plans; reapplying that empty override is safe.

## Scheduled RDP rule maintenance

The [EnsureRdpAccess function](functions/foundry-local-auth/EnsureRdpAccess/run.ps1)
runs every five minutes (`RDP_TIMER_SCHEDULE = 0 */5 * * * *`) in the same
Function App. It targets only these existing NSGs in `rg-vm-copilot`, subscription
`2524a5e1-00d7-43c2-a7cf-a87b79df2415`:

- `vm-copilot-nsg`
- `vnet-francecentral-1-snet-francecentral-1-nsg-francecentral`

It creates `Allow-RDP-Any`: inbound Allow TCP, source address/port `*`, destination
address `*`, destination port `3389`, priority `100`. A matching allow rule,
including an equivalent rule with a different name, is a no-op. A conflicting
rule named `Allow-RDP-Any` or an occupied inbound priority `100` causes an explicit
error rather than an overwrite. Existing matching rules retain their priorities;
this check does not evaluate effective rules, routing, host firewalls, or RDP
service availability. Range-based rules are not treated as equivalent.

This deliberately exposes RDP to **any source IP**. Prefer Azure Bastion, JIT, or
restricted source IPs where possible. Deleting the rule alone is not permanent:
the next successful timer invocation recreates it. Disable `EnsureRdpAccess`
before intentionally removing access. Azure Policy deny assignments still apply.

The function uses the existing `Az.Accounts` module's `Invoke-AzRestMethod` and
updates only the child security rule, not the NSG's entire rule collection.
Managed identity has NSG read and child-rule read/write permissions assigned only
on the two target NSGs. That Azure permission permits writing other security rules
within those NSGs; it does not grant NSG deletion, VM administration, or RBAC
changes. Both targets are attempted even if one fails, and any failure marks the
invocation failed in Application Insights. `RDP_NSG_IDS` contains the two approved
resource IDs; adding targets requires updating both the explicit allowlist and
Terraform RBAC assignments.
